# Code review

Read `<upstream>/code-review/SKILL.md` and follow it with these deviations. It becomes a three-axis review: Standards, Spec and **Correctness**, each reported separately.

- **`code-review`, step 1 (fixed point):** the fixed point is the merge-base with the base branch: `git fetch <remote>` and use `<remote>/<base>`. Don't ask the developer for it.
- **`code-review`, step 2 (spec source):** on the small route the spec is the issue, or the few-line spec the developer confirmed (pass its text to the Spec sub-agent). On the large route it is the spec issue and its tickets.
- **`code-review`, step 3 (standards sources):** the sources are always the conventions the settings name, the glossary (names in the code, tests, commit messages and docs follow its terms and avoid the ones it lists under _Avoid_), `docs/agents/domain.md` when it exists and the ADRs that touch the diff, plus anything else the step finds.
- **`code-review`, step 4 (sub-agents):** spawn a third sub-agent, **Correctness**, in parallel with the other two. Its prompt includes the diff command and commit list, and the brief: "Hunt for bugs the diff introduces. Read the changed code and what it calls, including the external APIs it relies on (<the settings' external APIs>): does the response really carry the field the code reads? Look for wrong results on concrete inputs, missed edge cases (empty, missing, duplicate, out-of-order), error paths that are swallowed or retried wrongly, races, and behaviour a test claims to cover but doesn't. Report each bug as file:line, the concrete input or state that triggers it, and what goes wrong; say whether you confirmed it (ran it, or traced it end to end) or it is plausible. No style remarks; that is the Standards axis. Under 400 words." Without external APIs in the settings, leave the parenthesis out.
- **`code-review`, step 5 (aggregate):** present the reports under `## Standards`, `## Spec` and `## Correctness`, unmerged and unranked across axes, and number every finding. Then **put the findings to the developer before fixing anything**: ask which to fix (for example "Fix S1, C2; skip S3?"). Judgement calls such as baseline smells stay theirs. Fix only the chosen findings, each as a separate commit, so the code review's effect is visible in the history. On the large route the fixes go to one fix subagent (see [LARGE.md](LARGE.md)).

After the fixes, run the settings' full checks once more.
